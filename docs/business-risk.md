# 业务风控 0.3

目标：为虚假 / 批量注册、设备作弊、营销滥用和支付欺诈提供可追溯的风险线索与处置建议。当前是观察模式规则基线，不是经过样本评估的欺诈概率模型，也不执行实际封禁、扣款、退款或奖励拦截。

## 接入位置

| 场景 | type | 推荐调用位置 | 关键业务数据 |
| --- | --- | --- | --- |
| 注册保护 | register | 创建账号之前 | 稳定的候选账号代号、服务端确认的用户 IP、SDK 报告 |
| 营销保护 | reward / coupon / withdraw | 发奖、领券、提现审批之前 | 活动代号、领取对象代号、账号、SDK 报告 |
| 支付保护 | payment | 发起一次支付尝试之前 | 订单代号、支付服务提供方的稳定支付工具代号、金额 / 币种、账号、SDK 报告 |
| 常规账号保护 | login 或其他自定义值 | 登录及关键操作 | 已认证账号、用户 IP、SDK 报告 |

register 事件表示注册尝试，不证明注册成功或账号实名。候选账号代号应在同一候选身份的重试之间稳定，例如业务侧以密钥派生的规范化联系方式代号；不要每次随机制造一个“新账号”。设备关联仍基于可伪造的 installationId，清数据 / 重装 / 改 ID 可影响关联。

账号、IP、活动、金额和支付工具代号由业务后端确认，应用密钥只存业务后端。SDK 只负责提供设备报告。接入方应使用自身支付服务的签名验证与业务归属校验，再提交真实支付回调结果。此服务不替代支付渠道验证。

## 业务上下文

`POST /v1/events` 原协议新增可选 context；原有必填 eventId / appId / reportId / accountId / type 保持。

```json
{
  "eventId":"reward-20261110-001",
  "appId":"应用ID",
  "reportId":"设备报告ID",
  "accountId":"业务账号代号",
  "type":"reward",
  "clientIp":"203.0.113.10",
  "context":{
    "campaignId":"newcomer-2026",
    "recipientId":"领取对象代号",
    "accountCreatedAt":"2026-11-10T12:00:00Z"
  }
}
```

payment 可提供 `orderId`、`paymentMethodId`、`amountMinor`、`currency`。金额使用最小货币单位的非负整数，正金额需带币种；当前不按金额跨币种比较。paymentMethodId 必须是业务后端取得的支付提供方稳定代号；平台不需要完整卡号、CVV、支付密码。相同支付工具在提供方生成不同 token 的情况下，不能直接认为 token 相同关系完整；需业务方选择正确关联粒度。

recipientId 是业务方用于奖励 / 提现归属判断的稳定代号，不要求提交真实银行卡号、手机号或地址。accountCreatedAt 由业务账号系统提供。缺少上下文时跳过对应规则，并在 missingFields 明确列出未覆盖字段；0 分只表示当前规则未命中。

客户端 IP 在入库前规范化，避免 IPv4 与等价映射 IPv6 写法分裂统计。同一事件重试也比较 context，修改订单、金额、活动等内容返回 409；更改策略后重试仍返回首次结果。

## 试运行规则

业务事件窗口按服务器接收时间计算，支付结果使用业务后端确认的发生时间，关联均限定在同一应用。distinct 账号、设备和支付工具计数，不能被相同 eventId 的网络重试增加。当前是各请求读取到的历史快照，不提供跨不同事件的强事务频控。

| 原因 | 窗口 / 默认触发条件（含当前事件） | 加分 |
| --- | --- | --- |
| 同设备集中注册 | 10 分钟，同设备至少 3 个不同候选账号 | 45 |
| 同网络集中注册 | 10 分钟，同 IP 至少 8 个不同候选账号 | 15 |
| 账号频繁切换设备 | 1 小时，同账号至少 3 个不同安装 ID | 25 |
| 同设备多账号参与活动 | 24 小时，同活动同设备至少 3 个不同账号 | 45 |
| 共用领取对象 | 24 小时，同活动同领取对象至少 3 个不同账号 | 40 |
| 重复领取尝试 | 1 分钟，同账号同活动至少 4 次不同业务事件 | 25 |
| 新账号集中参与活动 | 账号创建不足 1 小时，同活动同设备至少 2 个账号 | 15 |
| 支付尝试频繁 | 10 分钟，同账号至少 5 次支付尝试 | 25 |
| 更换支付工具 | 24 小时，同账号至少 3 个不同支付工具代号 | 25 |
| 共用支付工具 | 24 小时，同支付工具代号至少 3 个不同账号 | 40 |
| 近期支付失败 | 最近 1 小时，至少 3 笔不同尝试的最新真实结果为失败 | 35 |
| 近期拒付记录 | 最近 30 天，账号存在至少 1 笔最新结果为拒付的支付尝试 | 30 |

保留基础规则：调试 +15、模拟环境线索 +20、VPN +5、包名不一致 +30、24 小时同设备至少 4 个账号 +35、1 分钟同设备已有至少 10 个事件 +35。RootBeer 的 su / magisk / native-su 中至少两项 available=true，加 20；读取失败或缺失不加分。客户端线索始终可能被篡改。

分数封顶 100。默认 30 分起建议 verify；70 分起且涉及至少两个不同业务关联维度，营销 / 支付场景才建议 hold。例如“同设备多账号”与“同设备活动账号”属于同一维度，不因规则数量多就当作独立证据。单独共享网络 15 分保持 observe。阈值尚未校准，所有建议仍处于 shadow 模式。

返回新增：scene、action、mode、hits、missingFields、policy。hits 保存原因码、加分、数据来源、关联维度及可用的计数 / 阈值 / 时间窗。数据来源 client 表示自报环境，business 表示服务端业务事件关联，outcome 表示业务后端确认的支付结果。policy 保存当时完整阈值和版本。decision 保留 observe / review，供旧接入方兼容。

## 支付结果回流

业务后端在验证支付提供方回调后调用 `POST /v1/outcomes`，仍用该应用 Bearer 密钥：

```json
{
  "outcomeId":"支付提供方回调唯一号",
  "appId":"应用ID",
  "eventId":"原支付尝试的业务eventId",
  "status":"failed",
  "occurredAt":"2026-11-10T13:20:00Z"
}
```

status 支持 failed / succeeded / chargeback。只能引用同应用已存在的 payment 事件。首次 201；同 outcomeId 与同内容重试 200；内容冲突 409。每笔支付按 occurredAt 选择最新状态，相同发生时间再比较服务端接收时间；迟到的旧失败回调不会覆盖后来发生的成功。未来发生时间的结果不参与当前风险判断。一个支付尝试多个重复回调不会当成多笔失败。chargeback 是拒付观察值，不等同已经证实的欺诈。

## 策略与人工反馈

- `PUT /api/apps/{appId}/policy`：管理口令鉴权。字段为 reviewScore、holdScore、registrationAccounts、ipRegistrations、campaignAccounts、paymentMethods、paymentAccounts、paymentFailures。保存时生成新版本；与应用密钥分开存储，修改策略不覆盖密钥。
- `POST /api/events/{内部id}/reviews`：管理口令鉴权。body 为 label（fraud / legitimate / unknown）和可选 note。追加保存审核记录，不覆盖旧记录；后台显示最新反馈。此接口使用返回结果 id，不是业务 eventId。
- `/api/overview` 新增 scenes（24 小时场景数量）、feedback（按内部 id 的最新人工反馈）、outcomes（按内部 id 的最新支付结果）。事件详情可查看证据与录入反馈，应用管理可调整阈值。

人工标签用于收集评估样本，不自动修改历史评分或拉入永久黑名单。观察模式可以让业务方先测量命中量与误报，再自行决定何时把建议接入验证码、人工审核或暂缓发奖 / 支付的业务流程。当前没有调用这些实际处置系统。

## 验收与后续

本轮以合成场景验证：集中注册、共享 NAT 正常人群、跨应用隔离、活动串用边界、支付工具轮换与失败回调、回调乱序、重复事件、策略变更、反馈留痕。合成样例通过不代表识别率。

业务试点要分别记录：人工确认的异常与正常样本、每条规则的误报与漏报、核验通过率、真实奖励发放 / 支付结果，以及实际策略是否执行。只有接入真实业务结果后才能衡量损失变化；后台当前不展示“已挽回损失”等未经核实的指标。

设计参考：[OWASP 自动化威胁项目](https://owasp.org/projects/automated-threats-to-web-applications)用于确认业务功能滥用的场景范围；[Stripe 官方规则属性](https://docs.stripe.com/radar/rules/supported-attributes)用于核对支付事件、关联属性与结果计数的设计方向。本项目没有复用其风险模型、阈值或业务数据，上表为本项目待评测的规则设计。
